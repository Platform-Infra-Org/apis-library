# תורי משימות ועבודה ארוכה {#job-queues-and-long-running-work}

רבות מהפעולות שלנו לוקחות יותר זמן ממה שבקשת HTTP אמורה להישאר פתוחה: הרצת playbook, פריסה
הדרגתית ב-ArgoCD, שינוי מרובה שלבים שחוצה את Git, ‏Vault ו-ArgoCD. העמוד הזה מסביר את הרעיון של
תור משימות, למה AWX כבר נותן לכם אחד, ומה האפשרויות שלכם כשהוא לא מתאים. חוזה ה-API שנובע מזה
מפורט ב[תקני ה-API](../reference/api-standards.md#long-running-work).

## הרעיון {#the-concept}

**תור משימות** מפריד בין *קבלת* עבודה לבין *ביצוע* העבודה:

```
 client ──POST──▶ API ──enqueue(job)──▶ [ QUEUE ] ──▶ worker(s) ──▶ the actual work
   ▲               │                                       │
   │          202 {job_id}                          update job state
   └──GET /status/{job_id}──▶ API ──read state──▶ [ JOB STORE ] ◀┘
```

1. ה-API **מבצע ולידציה** לבקשה, **רושם** משימה, **דוחף** אותה לתור, ומחזיר מיד
   **`202 Accepted`** עם `job_id`.
2. ‏**worker** אחד או יותר לוקחים משימות מהתור ומבצעים את העבודה האיטית.
3. הלקוח **מתשאל** את `GET .../status/{job_id}` (או מקבל callback) עד שהמשימה מגיעה לסטטוס סופי,
   כמו `successful`, `failed` או `canceled`.

למה המבנה הזה חשוב:

- **ל-HTTP יש מגבלות זמן.** ‏Proxies, ‏ingress ולקוחות בדרך כלל מנתקים חיבורים אחרי 30–60 שניות.
  ‏playbook או פריסה הדרגתית ב-ArgoCD יכולים לקחת דקות.
- **עמידות:** משימה בתור שורדת הפעלה מחדש או פריסה של pod של ה-API. ‏handler של בקשה או משימה
  בזיכרון לא שורדים.
- **ויסות עומס (back-pressure):** פרץ של 500 בקשות הופך ל-500 משימות בתור שמטופלות בקצב מבוקר. הוא
  לא הופך ל-500 הרצות בו-זמניות.
- **ניסיונות חוזרים:** אפשר להריץ שוב משימות שנכשלו בלי שהלקוח ישלח אותן מחדש.
- **קנה מידה עצמאי:** ה-workers גדלים בנפרד מה-API, וכל רפליקה של ה-API יכולה לענות על קריאת
  הסטטוס.

תורים בדרך כלל מספקים משימה **לפחות פעם אחת**, כך שאותה משימה יכולה לרוץ פעמיים. לכן העבודה
שמשימה מבצעת חייבת להיות **אידמפוטנטית**: הרצה כפולה שלה משפיעה בדיוק כמו הרצה אחת.

## ‏AWX הוא כבר תור משימות {#awx-is-already-a-job-queue}

**‏AWX עובד בדיוק כמו תור משימות.** כש-API קורא ל-`awx.launch_job(...)`:

- ‏AWX **רושם** את המשימה ומחזיר `job_id` מיד. המשימה נמצאת במצב `pending`/`waiting` בתור של
  AWX עצמו.
- צמתי ההרצה של AWX משמשים בתור ה-**workers**: הם לוקחים את המשימה ומריצים אותה (`running`).
- ‏AWX **שומר את מצב המשימה ואת הפלט שלה** (`successful` / `failed` / `error` / `canceled`), והם
  שורדים הפעלות מחדש של ה-API שלכם.
- ה-API שלכם קורא את המצב הזה עם `awx.get_job_status(job_id)`, או מזרים את הפלט עם
  `awx.get_job_output(...)`.

לכן **API שמפעיל משימות AWX וחושף נתיב סטטוס כבר משתמש בתור משימות.** הוא לא צריך תור נוסף.
מודול ה-DNS ב-`example-api` פועל לפי הדפוס הזה: `POST /dns/` מפעיל את המשימה ומחזיר את ה-`job_id`
שלה, ו-`GET /dns/status/{job_id}` קורא אותה בחזרה מ-AWX.

זו גם הסיבה שתשובת ההפעלה של המחבר אומרת `status="successful"`: ‏AWX *קיבל* את המשימה לתור שלו,
אבל המשימה עוד לא הסתיימה. קריאת הסטטוס ממפה את המצבים של AWX ל-`status_code` בגוף התשובה:
`pending`/`waiting`/`running` → 202, `successful` → 200, `failed`/`error`/`canceled` → 500.
נתיב הסטטוס שלכם עדיין עונה עם HTTP 200: משימה שנכשלה היא תוצאה שהלקוח ביקש, לא שגיאה ב-API שלכם.

‏ArgoCD מתנהג בצורה אסינכרונית דומה: אתם מבקשים sync, ‏ArgoCD מבצע reconcile ברקע, ואתם מתשאלים
את `get_app_status`. מודול ה-HAProxy ב-`example-api` עובד כך.

## מתי צריך תור משלכם {#when-you-need-your-own-queue}

אם העבודה האיטית רצה **בתוך ה-API שלכם**, ולא ב-AWX או ב-ArgoCD, והיא חייבת לשרוד הפעלות מחדש,
לקבל ניסיונות חוזרים או לרוץ בקצב מוגבל, אתם צריכים תור משימות משלכם.

!!! warning "אין תור משימות בספרייה (בינתיים)"
    ‏`tashtiot-apis-library` לא כוללת מימוש של תור משימות. צוות שצריך תור כזה חייב **לממש אותו**
    או **להשתמש בפתרון חיצוני**, כמו message broker עם ספריית task queue. אפשרות נוספת היא למדל את
    העבודה כ**משימה או workflow ב-AWX**, וכך מקבלים את התור בחינם.

לא משנה באיזו אפשרות הצוות בוחר, תור שעובד נותן לכם:

- **משימות עמידות** ששורדות הפעלות מחדש.
- **מזהה משימה** ו**סטטוס** שכל רפליקה של ה-API יכולה לקרוא, כדי שה-API ישמור על אותו חוזה של
  `202` + `GET .../status/{job_id}` כמו במקרה של AWX.
- **ניסיונות חוזרים** לכשלים חולפים (timeouts, ‏5xx, ‏429), עם backoff ומספר מקסימלי של ניסיונות.
  שגיאות ולידציה או הרשאות לא יצליחו בניסיון חוזר, ולכן לא מנסים אותן שוב.
- **‏timeout** לכל משימה.
- מקום לשמור משימות שנכשלו לצורך בדיקה.

‏worker הוא פשוט עוד נקודת כניסה לאותו קוד. הוא בונה את המחברים פעם אחת וקורא לאותן פונקציות
ב-`operations.py` שה-API היה קורא להן.

## משימות רקע בתוך התהליך אינן תור {#in-process-background-tasks-are-not-a-queue}

‏`asyncio.create_task(...)` (או `BackgroundTasks` של FastAPI) מריץ עבודה אחרי שהתשובה נשלחה,
**בתוך התהליך של ה-API**. מודול ה-HAProxy ב-`example-api` עושה את זה עבור ההמתנה וה-sync של
ArgoCD. זה בסדר לעבודה קצרה ב-best-effort, אבל זה לא נותן אף אחת מההבטחות של תור:

- **המשימה הולכת לאיבוד בהפעלה מחדש, בפריסה או ב-OOM.** כל rollback שהיא הייתה אמורה להריץ לא
  קורה, וזה עלול להשאיר את Git ו-Vault מוחלים באופן חלקי.
- **המשימה חיה ברפליקה אחת.** נתיב סטטוס לא יכול לשאול עליה רפליקה אחרת, ולכן הסטטוס חייב להגיע
  מהמערכות החיצוניות. נתיב הסטטוס של HAProxy שואל את ArgoCD מהסיבה הזו.
- **אין ניסיונות חוזרים, אין ויסות עומס.**
- **הלולאה מחזיקה רק הפניה חלשה למשימה.** אם שום דבר אחר לא מפנה אליה, היא עלולה להימחק ב-garbage
  collection באמצע הריצה. שמרו את המשימות ב-set עד שהן מסתיימות:
    ```python
    _background_tasks: set[asyncio.Task] = set()


    def spawn(coro) -> None:
        task = asyncio.create_task(coro)
        _background_tasks.add(task)
        task.add_done_callback(_background_tasks.discard)
    ```
- **אף אחד לא ממתין למשימה**, ולכן חריגה שלא נתפסת ונרשמת ללוג בתוכה פשוט נעלמת.

## איך לבחור {#choosing}

| העבודה… | השתמשו ב- |
|---|---|
| מסתיימת בהרבה פחות מ-~5 שניות | **בתוך הבקשה:** המתינו לה עם await בבקשה |
| רצה כ**משימת AWX** (או sync של ArgoCD) | **‏AWX/ArgoCD כתור:** הפעילו אותה, החזירו 202 + המזהה, וחשפו נתיב סטטוס |
| קצרה, ב-best-effort, ומותר לאבד אותה בהפעלה מחדש (התראה, חימום מטמון) | **משימת רקע בתוך התהליך** |
| ארוכה, רצה בתוך ה-API שלכם, ואסור לאבד אותה, צריכה ניסיונות חוזרים או חייבת לרוץ בקצב מוגבל | **תור משימות משלכם**, שהצוות מימש או פתרון חיצוני |
| תקופתית (poller או לולאת סנכרון) | **`general_create_app(async_background_tasks=[...])`**. עותק אחד רץ בכל רפליקה, ולכן הפכו אותה לאידמפוטנטית. |
