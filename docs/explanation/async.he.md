# אסינכרוניות ולולאת האירועים {#async-and-the-event-loop}

כל מה שבספרייה הזו אסינכרוני: המחברים, לקוח ה-SSO היוצא, ספק ה-Remote Config ומשימות הרקע של
פונקציית יצירת האפליקציה. העמוד הזה מסביר מה זה אומר, למה בחרנו בזה על פני תכנון סינכרוני, ולמה
זה מחייב את כללי ה-async שב[תקני ה-API](../reference/api-standards.md#async-rules).

## מה זה "async" {#what-async-means}

תוכנית רגילה (**סינכרונית**) עושה דבר אחד בכל פעם. כשהיא קוראת לשירות אחר ברשת, ה-thread
**נחסם** ולא עושה כלום עד שהתשובה מגיעה. כדי לשרת 50 בקשות במקביל, שרת סינכרוני צריך בערך 50
threads או תהליכים, ורובם מבלים את זמנם בהמתנה.

תוכנית **אסינכרונית** רצה על **לולאת אירועים** (event loop): thread יחיד שמתמרן בין משימות רבות.
כשמשימה מגיעה לקריאת I/O איטית וממתינה לה עם `await`, היא מחזירה את השליטה ללולאה. הלולאה מריצה
בינתיים משימות אחרות, בזמן שהרשת או הדיסק עושים את שלהם, וממשיכה את המשימה הראשונה כשהתוצאה
מוכנה.

```python
# סינכרוני: ה-thread תקוע לאורך כל הסבב.
response = requests.get("https://awx/api/v2/jobs/42/")

# אסינכרוני: בזמן שהבקשה בדרך, לולאת האירועים משרתת בקשות אחרות.
response = await client.get("/api/v2/jobs/42/")
```

| מונח | משמעות |
|---|---|
| `async def` | מגדיר **פונקציית coroutine**. קריאה אליה מחזירה אובייקט coroutine; שום דבר לא רץ עד שממתינים לו או מתזמנים אותו. |
| `await x` | "עצור אותי כאן עד ש-`x` מסתיים, ובינתיים תן ללולאה להריץ דברים אחרים". מותר רק בתוך `async def`. |
| לולאת אירועים | המתזמן שמריץ את ה-coroutines. ‏uvicorn מפעיל לולאה אחת לכל תהליך worker. |
| משימה (Task) | coroutine שתוזמן על הלולאה (`asyncio.create_task(...)`) כדי לרוץ במקביל לאחרים. |
| קריאה חוסמת | כל דבר שתופס את ה-thread בלי `await` (‏`time.sleep`, `requests.get`, דרייבר DB סינכרוני, עבודת CPU כבדה). |

!!! note
    אסינכרוניות היא **מקביליות בהמתנה, לא בחישוב**. היא חופפת בין *המתנות*, לא בין *חישובים*.
    לולאת אירועים אחת עדיין משתמשת בליבת CPU אחת.

## למה async ולא APIs סינכרוניים {#why-async-instead-of-sync-apis}

ה-APIs שלנו הם **מתזמרים** (orchestrators). בקשה טיפוסית מאמתת את הקלט, קוראת ל-AWX, ‏ArgoCD,
‏Vault, ‏Bitbucket, ל-Config API או לנקודת הטוקנים של ה-SSO, ומחזירה תשובה. כמעט כל זמן הבקשה
מבוזבז על **המתנה למערכות אחרות**, ובדיוק לזה async נועד.

- **תפוקה לכל pod:** ‏worker אחד יכול להחזיק מאות בקשות פתוחות מול שירותים איטיים בלי thread לכל
  אחת, ולכן צריך פחות רפליקות ופחות זיכרון.
- **פיצול מובנה:** קריאות בלתי תלויות יכולות לרוץ בו-זמנית עם `asyncio.gather`, כך שהבקשה לוקחת
  כמו הקריאה האיטית ביותר ולא כמו סכום כל הקריאות.
- **המתנה זולה:** ‏`await asyncio.sleep(5)` בתוך לולאת "המתן למשימת AWX" לא עולה כלום.
  ‏`time.sleep(5)` היה חוסם worker שלם.
- **עבודת רקע בתוך התהליך:** משימות אתחול, כמו הסנכרון התקופתי של רשימות ה-Remote Config, רצות על
  אותה לולאה כמו הטיפול בבקשות.
- **מודל אחד מקצה לקצה:** ערבוב של קוד סינכרוני ואסינכרוני מחייב מעברים בין threads ומסתיר באגים.
  כשהכול אסינכרוני, המודל נשאר פשוט.

## איך הספרייה אסינכרונית {#how-the-library-is-async}

- **כל מתודה של מחבר היא coroutine.** ‏`AWX`, `ArgoCD`, `Git` ו-`Vault` חושפים רק מתודות
  `async def`, ולכן חייבים להמתין להן עם `await`
  ([ארכיטקטורה](architecture.md#the-three-layer-connector-pattern)).
- **כל ה-HTTP היוצא עובר דרך `BaseAPI`**, עטיפה דקה שבונה `httpx.AsyncClient`. כשמשתמשים בו בצורה
  `async with BaseAPI(...) as client:`, הוא סוגר את מאגר החיבורים בסוף הבלוק.
- **‏Git משתמש בתהליכי משנה אסינכרוניים.** המחבר `Git` מריץ את `git` מעל SSH עם
  `asyncio.create_subprocess_exec`, כך שגם הרצת פקודות חיצוניות לא חוסמת את הלולאה.
- **פונקציות ההמתנה מתשאלות עם `asyncio.sleep`.** ‏`AWX.wait_for_job_completion` ו-
  `ArgoCD.wait_for_app_creation` הן דוגמאות. המתנה ארוכה עולה coroutine ישן, לא thread.
- **גם ה-SSO היוצא וה-Remote Config אסינכרוניים.** קבלת טוקנים ושליפת קונפיגורציה מהשירות החיצוני
  נעשות עם `await`, והתוצאות נשמרות במטמון
  ([תכנון האימות](authentication.md#outbound-client_credentials-cached-and-refreshed)).
- **מחזור החיים של האפליקציה מריץ coroutines ברקע.** ‏`general_create_app` מפעיל כל coroutine
  שב-`app.state.async_background_tasks` בעליית השירות, ומבטל אותם בכיבוי.

## ההשלכות: למה הכללים קיימים {#consequences-why-the-rules-exist}

מכיוון ש-thread אחד משרת את כל הבקשות ב-worker, **קריאה חוסמת אחת עוצרת את כולן**. ‏
`time.sleep(5)` בנתיב אחד אומר שאף בקשה אחרת באותו worker לא מקבלת תשובה במשך חמש שניות. זו
הסיבה לכל אחד מ[כללי ה-async](../reference/api-standards.md#async-rules):

- **ספריות I/O סינכרוניות אסורות בקוד אסינכרוני.** ‏`requests` ודרייברים סינכרוניים של DB חוסמים
  את הלולאה. החלופות האסינכרוניות (‏`httpx`, דרייברים אסינכרוניים) מחזירות לה את השליטה.
- **עבודה חוסמת שאי אפשר להימנע ממנה עוברת ל-thread** עם `asyncio.to_thread`. הלולאה ממתינה ל-
  thread במקום להיתקע בתוך הקריאה.
- **נתיבים שמוגדרים עם `def` רגיל רצים ב-thread pool.** ‏FastAPI מריץ אותם במאגר של כ-40 threads
  כברירת מחדל, כדי שלא יחסמו את הלולאה. זה בסדר לנתיבים פשוטים שעושים רק חישוב, אבל שימוש בזה כדי
  לקרוא ל-I/O סינכרוני רק מעביר את צוואר הבקבוק למאגר.
- **לכל המתנה ברשת צריך timeout.** קריאה שממתינים לה ולעולם לא חוזרת לא חוסמת בקשות אחרות, אבל
  היא מחזיקה את הבקשה שלה ואת החיבור שלה פתוחים לנצח.
- **משימות צריכות הפניה.** הלולאה מחזיקה רק הפניה חלשה למשימה שנוצרה עם `asyncio.create_task`,
  ולכן משימה שאף אחד לא מחזיק בה עלולה להימחק באמצע הריצה (ראו
  [תורי משימות ועבודה ארוכה](job-queues.md#in-process-background-tasks-are-not-a-queue)).
- **אל תפעילו לולאה בתוך האפליקציה.** ‏`asyncio.run()` נכשל בתוך לולאה שכבר רצה, ו-uvicorn כבר
  מריץ אחת.
