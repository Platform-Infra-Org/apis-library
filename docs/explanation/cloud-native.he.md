# APIs מבוססי ענן (cloud-native) ורפליקות מרובות {#cloud-native-apis-and-multiple-replicas}

ה-APIs שלנו רצים על Kubernetes (‏OpenShift) בתור **כמה רפליקות זהות** של אותו קונטיינר. העמוד הזה
מסביר מה זה אומר לגבי הדרך שבה כותבים API, ולמה
[תקני ה-API](../reference/api-standards.md#multiple-replicas) מתעקשים על קוד חסר מצב (stateless)
ואידמפוטנטי.

## מהי רפליקה {#what-a-replica-is}

‏Deployment מריץ **N pods** מאותו image. ‏Service שעומד לפניהם מפזר את הבקשות הנכנסות בין
ה-pods:

```
                         ┌──▶ pod A  (uvicorn, one event loop, own memory)
client ──▶ Service / LB ─┼──▶ pod B  (uvicorn, one event loop, own memory)
                         └──▶ pod C  (uvicorn, one event loop, own memory)
```

הפלטפורמה מריצה כמה רפליקות בשביל:

- **זמינות:** pod יכול למות, להיות מפונה (evicted) או לעבור לצומת אחר בכל רגע, והאחרים ממשיכים
  לשרת.
- **פריסות בלי השבתה:** עדכון מתגלגל (rolling update) מחליף pods אחד אחד, כך שלמשך זמן מה **הגרסה
  הישנה והחדשה רצות זו לצד זו**.
- **קנה מידה:** יותר עומס פירושו יותר pods, בין שמגדירים אותם ידנית ובין שעושה זאת autoscaler.

העובדה המרכזית: **ל-pods אין שום דבר משותף.** לכל אחד יש זיכרון משלו, לולאת אירועים משלו, מערכת
קבצים משלו ומשימות רקע משלו. שתי בקשות עוקבות מאותו לקוח יכולות להגיע ל-pods שונים.

## ההשלכות על קוד ה-API {#consequences-for-api-code}

### השאירו את המצב מחוץ לתהליך {#keep-state-out-of-the-process}

כל מה שנשמר במשתנה Python גלוי ל-pod **אחד** בלבד, ורק עד שה-pod הזה מופעל מחדש. לכן:

- **אל תחזיקו את מקור האמת בזיכרון.** זה כולל סטטוס של משימות, דגלי "בתהליך", sessions, מונים
  וכל דבר שבקשה מאוחרת יותר צריכה. ‏`POST` ב-pod A ואחריו `GET .../status` ב-pod B חייבים לעבוד.
  הסטטוס מגיע מהמערכת שאחראית עליו (AWX, ‏ArgoCD, ‏Git, ‏Vault) או ממאגר משותף, ולכן
  [העמוד על תורי משימות](job-queues.md#in-process-background-tasks-are-not-a-queue) גוזר את
  הסטטוס מהמערכת החיצונית.
- **מטמון זה בסדר, כל עוד הוא רק מטמון.** הספרייה שומרת במטמון טוקני SSO, מפתחות JWKS ותשובות
  של Remote Config **בכל pod בנפרד**. זה בטוח, כי החטאה במטמון פשוט שולפת מחדש. מטמון לעולם לא
  יכול להחזיק את העותק היחיד של משהו.
- **מערכת הקבצים המקומית זמנית ופרטית ל-pod.** אל תכתבו קבצים שבקשה אחרת או הפעלה מחדש צריכות.
  סודות שמותקנים לקריאה בלבד (למשל מפתח ה-SSH של Git) הם בסדר.

### צפו שאותה עבודה תגיע פעמיים, ל-pods שונים {#expect-the-same-work-to-arrive-twice-on-different-pods}

לקוחות ו-proxies מנסים שוב, משתמשים לוחצים פעמיים, ובקשה יכולה לחרוג מה-timeout ב-pod A ולהישלח
שוב ל-pod B. שני pods יכולים גם לטפל ב"צור X" עבור אותו שם **באותו רגע**.

- **הפכו פעולות לאידמפוטנטיות:** יצירה, עדכון או מחיקה חוזרים מובילים לאותה תוצאה סופית
  (ראו [תקני API → פעולות מרובות שלבים](../reference/api-standards.md#multi-step-operations)).
- **השתמשו בשמות דטרמיניסטיים**, שנגזרים מהבקשה, כדי שניסיון חוזר יפנה לאותו משאב.
- **תנו למערכת החיצונית להכריע.** ‏`asyncio.Lock` מסדר בקשות בתור רק בתוך pod אחד, ולכן הוא לא
  יכול למנוע מרוץ בין שני pods. הסתמכו על זיהוי ההתנגשויות של השירות החיצוני (upstream) עצמו:
  ‏`add_file` של המחבר `Git` זורק `GitError` עם סטטוס 409 כשהנתיב כבר קיים, ו-`create_app` של
  ‏ArgoCD (עם ברירת המחדל `upsert=False`) דוחה Application שכבר קיים עם spec שונה. תרגמו את
  ההתנגשויות האלה ל-`409`.
- **"בדוק ואז כתוב" הוא מרוץ בין רפליקות.** "קרא את הסוד, ואם הוא חסר, כתוב אותו" יכול להשתלב בין
  שני pods. קבלו את זה, ושמרו על הכתיבה עצמה אידמפוטנטית, או העבירו את ההגנה למערכת שמציעה פעולה
  אטומית.

### משימות רקע רצות פעם אחת לכל רפליקה {#background-tasks-run-once-per-replica}

כל coroutine ב-`general_create_app(async_background_tasks=[...])` מתחיל לרוץ ב-**כל** pod.

- **לולאות לקריאה בלבד ואידמפוטנטיות הן בסדר.** ה-poller של רשימת הערכים המותרים של Remote Config
  רץ N פעמים, וזה פשוט אומר N רענונים.
- **עבודה שחייבת לקרות פעם אחת** ("נקה X שפג תוקפו כל שעה", "שלח את הדוח היומי") לא יכולה להיות
  לולאה בתוך התהליך, אחרת היא תרוץ N פעמים. השתמשו במשהו שרץ פעם אחת מעצם תכנונו: CronJob של
  Kubernetes, תזמון ב-AWX, או תור משימות עם צרכן יחיד.
- **משימה שהופעלה עם `asyncio.create_task` מתה יחד עם ה-pod שלה.** עדכון מתגלגל הורג pods בכוונה,
  ולכן כל דבר שחייב להסתיים שייך ל-AWX או לתור משימות
  ([תורי משימות ועבודה ארוכה](job-queues.md)).

### עלייה מהירה, כיבוי נקי {#start-fast-stop-cleanly}

‏Pods מופעלים ונעצרים כל הזמן, ולכן שתי הפעולות צריכות להיות זולות ובטוחות:

- **עלייה:** שגיאות קונפיגורציה צריכות להיכשל מהר, וכך זה קורה: הגדרות חובה וקונפיגורציית אימות
  שגויה עוצרות את האפליקציה כבר ביצירתה. עבודה כבדה לא שייכת לזמן ה-import.
- **כיבוי:** ‏Kubernetes שולח `SIGTERM`, ממתין לתקופת החסד (30 שניות כברירת מחדל), ואז הורג את
  ה-pod. ‏uvicorn מפסיק לקבל חיבורים ומאפשר לבקשות שבטיפול להסתיים, וה-lifespan של הספרייה מבטל
  את משימות הרקע. שמרו על בקשות קצרות (עבודה ארוכה עוברת למשימה), כדי שיסתיימו בתוך תקופת החסד.
- **‏Probes:** ‏`/liveness` עונה על "האם התהליך חי?", ו-`/readiness` עונה על "האם ה-pod הזה צריך
  לקבל תעבורה?". הספרייה מגישה את שניהם ומחריגה אותם מאימות ומלוגים של בקשות. הם מדווחים רק על
  התהליך, לא על השירותים החיצוניים. אל תגרמו ל-liveness להיות תלוי ב-AWX או ב-Vault, אחרת תקלה
  בשירות חיצוני תגרום ל-Kubernetes להפעיל מחדש את כל ה-pods בבת אחת.

### שתי גרסאות רצות באותו זמן {#two-versions-run-at-the-same-time}

במהלך עדכון מתגלגל, pods של גרסה *n* ושל גרסה *n+1* משרתים תעבורה יחד, ולקוח עשוי להגיע לשתיהן
בתוך תהליך עבודה אחד.

- שינויים חייבים להיות **תואמים לאחור** למשך שחרור אחד לפחות: שדות חדשים בבקשה הם אופציונליים,
  ושדה בתשובה לא מוסר או משנה את שמו במקום.
- שינויים שוברים נכנסים ל**גרסת API חדשה** (`/v2/...`) לצד הישנה
  ([תקני API → נתיבים וגרסאות](../reference/api-standards.md#paths-and-versioning)).
- התנהגות רקע חדשה וכתיבות חדשות לשירותים חיצוניים חייבות להיות בטוחות כל עוד pods ישנים עדיין
  רצים.

### הניטור הוא לכל pod {#observability-is-per-pod}

- **לוגים** נכתבים ל-stdout (הספרייה מגדירה את Loguru כך). הפלטפורמה אוספת אותם מכל pod, ולכן
  לעולם אל תכתבו קובצי לוג. כללו מזהים (`job_id`, `app_name`, `metadata.project`) כדי שאפשר יהיה
  לעקוב אחרי פעולה אחת לאורך כמה pods.
- **מטריקות** ב-`/metrics` מתארות **pod אחד**. ‏Prometheus אוסף מכל pod בנפרד, ולכן הדשבורדים
  מצרפים נתונים מכל ה-pods (`sum by (...)`), ומונה של pod בודד כשלעצמו אינו הסך הכולל של ה-API.

### הגדילו עם רפליקות, לא עם תהליכים {#scale-with-replicas-not-processes}

הריצו **תהליך uvicorn אחד לכל pod** (כמו שעושה ה-`CMD` של `example-api`) ותנו ל-Kubernetes להוסיף
pods. לכמה תהליכי worker בתוך pod אחד יש אותן השלכות של היעדר זיכרון משותף כמו לרפליקות, אבל הם
מסתירים אותן מהתזמון, מה-probes וממגבלות המשאבים של הפלטפורמה.
